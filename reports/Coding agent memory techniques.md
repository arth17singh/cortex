# Index the raw history, don't replace it

The strongest result in 2023–2026 memory research is that long-term memory works when the raw conversation stays searchable and is what the answering model reads. Extracted facts work best as index keys, as pointers and as a current-state layer; used as a substitute for the raw text, they lose details. Appending extracted facts to each raw item's index text raised **BM25 Recall@5 on LongMemEval's chat turns from 0.472 to 0.554** ([LongMemEval](https://arxiv.org/html/2410.10813)). Extraction-only pipelines kept as little as **2–3% of memory points on long histories** ([HaluMem](https://arxiv.org/html/2511.03506)) and scored about **half of what plain BM25 over raw chunks scored** on the independent MemoryAgentBench ([MemoryAgentBench](https://arxiv.org/html/2507.05257)). That suits a stdlib-only design. Going without embeddings costs 9–19 Recall@5 points on raw chat history, most on single turns, and under 4 points on whole sessions once fact keys are added. Every model step with evidence behind it (expansion, extraction, conflict judging, summaries) runs at index time, where 5–7 s Haiku calls are affordable. In order, the highest-impact moves for CORTEX are a line-addressed transcript layer that includes assistant turns and carries record statements as index keys; query variants written by Claude plus reading rules, because **40–50% of LongMemEval errors happen after retrieval already succeeded**; a small curated core that is read whole; explicit supersession behind a strict capture gate; and small or empty injection packs when evidence is thin. Graphs, community summaries, decay scores and sleep-time consolidation have weak or no evidence for this use. Graphs help bridge-entity questions and hurt simple ones, so they belong behind BM25 as an opt-in re-ranker. Coding-agent vendors are moving away from agent-written memories toward curated rules files. The only published coding-memory A/B test (GitHub Copilot, **90% vs 83% PR merge rate**) used memories whose code citations are re-checked before use ([GitHub](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/)). Most leaderboard margins come from configuration and judge choices, and no independent benchmark covers cross-session memory on a developer's own project. CORTEX's 90-question held-out set resolves only differences of about 8 points, so its −3.6-point gap between records-first v7 and curated v5 matches what the literature predicts but does not yet prove it.

## Five of fifteen techniques carry most of the expected gain

The ranking scores each technique on three things. The first is how strong and independent its evidence is. The second is how often the failure it fixes shows up in project-history questions: decisions, rejected options, rationale, current status and dependencies. The third is whether it fits a stdlib process that answers in under 0.5 s, with model calls only in background jobs. Impact is a judgment drawn from the evidence in the sections that follow, not a measurement.

| # | Technique | Impact here | Evidence | Fits the constraints? | Design move |
|---|---|---|---|---|---|
| 1 | Raw history as the value, records appended to its index keys | High | Strong, independent ([LongMemEval](https://arxiv.org/html/2410.10813)) | Yes: Haiku at index time, BM25 at query time | Index user and assistant passages plus the statements of records citing them; return lines with the current record on top |
| 2 | Query variants written by Claude, iterative search, reading rules | High | Moderate: independent error analysis, vendor agent result ([LongMemEval](https://arxiv.org/html/2410.10813)) | Yes: Claude writes, the script fuses | 2–4 phrasings per call fused by RRF; rules to open cited lines and answer every part |
| 3 | Small curated core read whole, re-injected after compaction | High | Moderate: vendor convergence, local result ([Windsurf docs](https://docs.windsurf.com/es/windsurf/cascade/memories.md)) | Yes | Curated notes stay primary; records never replace reading them |
| 4 | Inverted BM25 index with fast load, stopwords, identifier splitting | Prerequisite | Strong for BM25; latency measured locally ([MemoryAgentBench](https://arxiv.org/html/2507.05257)) | Yes, about 0.35 s worst case at 100k chunks | Packed arrays or FTS5, not a dict-of-lists cache |
| 5 | Explicit supersession on bi-temporal fields, Graphiti-style judge | Medium–high | Problem strong, fix untested ([MemoryAgentBench](https://arxiv.org/abs/2507.05257)) | Yes | Compare event dates; show current records with chains; score update decisions |
| 6 | Strict capture gate | Medium–high | Moderate, independent, non-coding agents ([Xiong et al.](https://arxiv.org/abs/2505.16067)) | Yes, background | Measure capture precision on labelled turns first |
| 7 | Small or empty injection packs when evidence is thin | Medium | Moderate, independent ([Sufficient Context](https://arxiv.org/abs/2411.06037)) | Yes | Silent, or "no matching record", on unmatched terms or flat scores |
| 8 | More index-time expansion: metadata headers, filtered generated questions | Medium | Strong in-domain, small out of domain, untested with LLM generators ([doc2query--](https://arxiv.org/abs/2301.03266)) | Yes, background | Deterministic headers first; keep a generated question only if it retrieves its own source |
| 9 | Injection hygiene on the capture path | Safety, no accuracy gain | Threat and spotlighting both strong ([Spotlighting](https://arxiv.org/abs/2403.14720)) | Yes | User and assistant text only; provenance tags; memory never triggers tools |

| 11 | Commit messages as episodic memory | Low–medium | Moderate, independent ([RepoMem](https://arxiv.org/html/2510.01003v2)) | Yes | BM25 over git log with commit provenance |
| 12 | Summaries indexed as ordinary BM25 documents | Low–medium | Moderate ([RAPTOR](https://arxiv.org/html/2401.18059)) | Yes, background | Per-session and per-subject summaries as extra candidates only |
| 13 | Graph expansion and personalised PageRank | Low; bridge questions only | Strong on bridge questions, harmful on simple ones, no lexical test ([HippoRAG 2](https://arxiv.org/html/2502.14802)) | Yes, with forward push | Opt-in re-ranker seeded by BM25, never a router |
| 14 | Sleep-time consolidation and reflection | Unknown | Weak: maths and believability proxies ([sleep-time compute](https://arxiv.org/abs/2504.13171)) | Yes, background | Measure as an intervention; outputs stay separate, linked records |
| 15 | Time decay, importance scores, age-based deletion | None to negative | Never ablated; periodic deletion hurt ([Xiong et al.](https://arxiv.org/abs/2505.16067)) | Yes | Recency only breaks ties among current records |

The constraints rule out four families of technique, and each has a substitute inside the agent. Dense embeddings give way to BM25 with key expansion. LLM reranking is too slow: about 11–32 s per query for RankGPT ([RankGPT](https://arxiv.org/html/2304.09542)) and 6.1 s per query on CPU for a cross-encoder ([BEIR](https://arxiv.org/html/2104.08663)). Claude reading the top 20 hits does that job within its own turn. Query-time rewriting (HyDE, query2doc, decomposition) becomes phrasings that Claude writes into its search call. Per-query time-range extraction helped LongMemEval only when a GPT-4o-class model did the extracting ([LongMemEval](https://arxiv.org/html/2410.10813)); here it becomes stored dates used as filters. The top five share a trait: none is a new memory structure. Each is a decision about what gets indexed, what the reader sees and which model does the thinking.

## Extracted facts add 8 recall points as keys and lose details as replacements

The memory systems built since 2023 divide on one choice: whether the raw conversation survives extraction. Zep keeps raw messages as a "non-lossy" episode store beneath its bi-temporal fact graph ([Zep](https://arxiv.org/html/2501.13956)). A-MEM keeps the original text inside every note ([A-MEM](https://arxiv.org/html/2502.12110)). MemGPT keeps the full message history in recall storage while a small working context stays loaded ([MemGPT](https://arxiv.org/html/2310.08560)). Claude Code already has those tiers: CLAUDE.md is the core memory and the JSONL transcripts are the recall storage.

Mem0 keeps only extracted facts, and its own paper shows the price. On LoCoMo, **full context scored 72.90 against 66.88 for Mem0 and 68.44 for its graph variant**. Mem0's real gains were in cost: 1,764 instead of 26,031 context tokens, and a p95 latency of 1.44 s instead of 17.12 s ([Mem0](https://arxiv.org/html/2504.19413)). HaluMem measured extraction directly; its authors overlap with the MemOS team, which tops its tables. Recall stayed under 60% for every system except MemOS. **Mem0 kept 42.91% of memory points on medium-length histories and 3.23% on long ones**, and most systems missed more than half of the updates ([HaluMem](https://arxiv.org/html/2511.03506)). On the independent MemoryAgentBench, BM25 over raw 512-token chunks scored 41.5 overall, against 24.0 for Zep, 21.1 for Mem0, 20.6 for Cognee and 28.3 for MemGPT ([MemoryAgentBench](https://arxiv.org/html/2507.05257)). The 2025 "memory OS" designs (MemoryOS, MIRIX, LightMem, MemOS) add layered or typed stores, offline consolidation and lifecycle metadata. Their headline numbers fall when other teams re-run them.

LongMemEval, the most controlled evidence, compares three ways of using extracted facts, and only one helps. When facts or summaries replace the raw text the reader sees, accuracy drops "due to information loss". The one exception is multi-session questions, where decomposed facts help with aggregation. When facts are indexed as separate entries whose rankings are then merged ("rank merging"), dense Recall@5 on single rounds fell from 0.582 to 0.478. The authors attribute this to an index (m+1) times larger, and only a dense retriever was tested. When facts are appended to the raw item's own index text ("key merging"), they help. Round Recall@5 rose from 0.582 to 0.644, and GPT-4o's top-10 accuracy from 0.670 to 0.720. In the paper's retriever table, **the same expansion lifted BM25 from 0.472 to 0.554 on rounds and from 0.634 to 0.683 on sessions** ([LongMemEval](https://arxiv.org/html/2410.10813)). The paper's average gains, +9.4% recall and +5.4% accuracy, appear to be relative. Keyphrases or summaries used as keys did not help. A search whose main evidence is extracted records sits close to the lossy setup. A transcript layer whose passages carry their records' statements as extra index terms is the setup that works.

The most consistent pattern across papers matters most for coding agents: systems that extract or compress collapse on questions about what the assistant said. Zep lost 6.8 and 14.2 points to full context on LongMemEval's single-session-assistant questions ([Zep](https://arxiv.org/html/2501.13956)). In MemOS's runs on the same category, Mem0 scored 26.8, Memobase 23.2 and MemU 19.6 ([MemOS](https://arxiv.org/html/2507.03724)). LightMem scored **32.14, against 98.21 for naive RAG over raw turns** ([LightMem](https://arxiv.org/html/2510.18866)). These extractors are built around the user's facts and preferences. In a Claude Code project, much of what matters is said by the assistant: the options it proposed, what it built, what it rejected and why. A memory whose raw layer drops assistant turns, or whose extractor treats them as second-class, throws away the content that coding questions ask about.

History length decides whether to retrieve at all. LoCoMo's public conversations run about 16k–26k tokens and fit in context, so full context beats every memory product on them. Even MIRIX's own table shows full context at 87.52 against MIRIX's 85.38 ([MIRIX](https://arxiv.org/html/2507.07957)). On LongMemEval_S, at about 115k tokens per question, the picture reverses. GPT-4o falls **from 0.870 when given only the evidence to 0.606 when given the full history** ([LongMemEval](https://arxiv.org/html/2410.10813)). Zep beats full context, 71.2 to 60.2 ([Zep](https://arxiv.org/html/2501.13956)). A vendor's tuned RAG reached 82.4%; it matched individual turns, returned whole sessions and reranked them with a neural model ([Emergence](https://www.emergence.ai/blog/sota-on-longmemeval-with-rag)). Anthropic's own guidance is to skip retrieval below about 200k tokens and load everything with prompt caching ([Anthropic](https://www.anthropic.com/news/contextual-retrieval)). CORTEX's real corpus already holds about 161k readable tokens across seven transcripts ([handoff](../tests/HANDOFF.md)), and its curated notes are a small fraction of that. The curated core therefore belongs in context whole. Retrieval earns its place on the raw history, which has already outgrown comfortable reading.

Once retrieval is decent, the reader becomes the bottleneck. In LongMemEval's error analysis, a correct answer needed correct retrieval about 90% of the time. Yet cases where retrieval was right and the answer wrong made up **15–19% of all questions, or 40–50% of the errors**. Chain-of-Note reading over JSON-formatted items added up to about 10 points ([LongMemEval](https://arxiv.org/html/2410.10813)). With perfect evidence, switching the reader from GPT-4o to o3 moved accuracy 9.6 points in one harness ([Emergence](https://www.emergence.ai/blog/sota-on-longmemeval-with-rag)). Letta reported 74.0% on LoCoMo for an agent given the raw conversation as a file plus grep and file search, against 68.5% for Mem0's graph variant. That is a vendor result, its file search uses embeddings, and LoCoMo fits in context anyway ([Letta](https://www.letta.com/blog/benchmarking-ai-agent-memory)). CORTEX shows the same pattern. The fixed v7 raised judge-free reference recall on relational questions from .38 to .48, but relational accuracy rose only from .738 to .771. On the held-out set, **v7 scored 0.792, against 0.828 for curated v5 notes plus grep and 0.806 for grep alone**. That is a v7 − v5 difference of −3.6 points, with a 95% CI from −9.4 to +2.2 ([progress log](../tests/PROGRESS.md)).

What this calls for is mostly re-wiring, not a new store. Line-addressed passages of user and assistant text become the unit of evidence. Each passage gets an index document made of its own words plus the statements and subjects of every record whose `source` points into it. Matching happens on those small units, where fact keys help BM25 most. The pack then returns the parent window (the surrounding lines or session segment), with the current record printed as a one-line header. This is the turn-match, session-return pattern behind the 82.4% result, minus its neural reranker. Records stay retrievable on their own only for what facts do well: current state, supersession history and aggregation across sessions. The transcript-layer prototype committed on 4 November, scored on dev-set reference recall, points this way ([prototype](../tests/tools/proto_retrieval.py)). Key merging is the variant with published evidence behind it; records competing with passages as separate documents is not.

## BM25's 9–19 point deficit on chat history shrinks with bigger units and fact keys

Dropping embeddings costs less than it seems, and the cost depends on the size of the item being retrieved. In LongMemEval's own retriever comparison, BM25 over raw text trailed the Stella V5 dense model by **8.6 Recall@5 points on whole sessions (0.634 vs 0.720) and 18.8 on single rounds (0.472 vs 0.660)**. With fact keys, BM25 reached 0.683 on sessions, 3.7 points short of Stella without them ([LongMemEval](https://arxiv.org/html/2410.10813)). On MemoryAgentBench, BM25 averaged 41.5 overall, against 38.2 for Qwen3-Embedding-4B and 38.0 for text-embedding-3-large. It led the embedding retrievers on single-hop QA (66.0), multi-hop QA (56.0) and EventQA (74.6). It trailed OpenAI embeddings only on the benchmark's LongMemEval-style chat task (45.3 vs 48.3–50.3) ([MemoryAgentBench](https://arxiv.org/html/2507.05257)). What embeddings buy is robustness to paraphrase on short conversational items. Tokenisation and parameters recover a little of it: Snowball stemming raised BM25's BEIR average from 38.4 to 39.7 nDCG@10, and k1 = 0.9, b = 0.4 beat Lucene's defaults, 41.1 to 39.9 ([BM25S](https://arxiv.org/html/2407.03618)). That is consistent with the b ≈ 0.5 CORTEX already uses.

The lexical methods with the strongest evidence move all model work to index time. doc2query-- appended T5-generated questions to each passage after a relevance model filtered out the bad ones. That lifted BM25's MS MARCO RR@10 from **0.185 to 0.323**. Unfiltered generation reached only 0.279, because hallucinated terms hurt ([doc2query--](https://arxiv.org/abs/2301.03266)). SPLADE-doc, which needs no query encoder, reached a similar 0.322 ([SPLADE v2](https://arxiv.org/pdf/2109.10086)). Out of domain the gain shrinks: docT5query averaged only +1.6% over BM25 across 18 BEIR datasets ([BEIR](https://arxiv.org/html/2104.08663)), and no source tests an LLM such as Haiku as the generator for BM25. Anthropic's Contextual Retrieval looks like a lexical technique, but all three of its headline failure reductions include contextual embeddings. Adding contextual BM25 on top moved top-20 failures from 3.7% to 2.9%, and no BM25-only figure exists ([Anthropic](https://www.anthropic.com/news/contextual-retrieval)). The mechanism still suits BM25, because a header adds the document-level vocabulary a chunk lacks. For CORTEX, most of that header (session title, date, subjects, record type) is metadata it already holds, so it needs no model call.

The query-side methods with the largest gains all need a model call at query time. query2doc's pseudo-documents lift BM25 by 3–15% ([Query2doc](https://arxiv.org/abs/2303.07678)). Interleaving retrieval with reasoning (IRCoT) raised BM25 Recall@5 on 2Wiki from 61.9 to 75.6 ([HippoRAG](https://arxiv.org/html/2405.14831)). In a coding agent the caller is already a frontier model writing the search call, so Claude can write the alternative phrasings and the script can fuse the result lists at a few milliseconds per query. Reciprocal rank fusion with k = 60 is the default way to combine them. In Cormack's TREC tests it beat the best input run by about 4–5% MAP, and moving k between 20 and 80 changed MAP by about 0.001 ([Cormack et al.](https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf)). Its arithmetic rewards agreement: a document ranked 20th in two lists outscores one ranked first in a single list. A source that finds what nothing else finds, such as a graph, therefore needs a reserved slot or a weight. BM25F weights each field before term-frequency saturation, which suits structured records better than summing per-field scores ([BM25F](https://ir.webis.de/anthology/2004.cikm_conference-2004.6)). Pseudo-relevance feedback does not suit a reader who looks only at the top ten: RM3 lowered MS MARCO dev RR@10 from 0.184 to 0.157, even as it raised deep recall ([Pyserini](https://castorini.github.io/pyserini/2cr/msmarco-v1-passage.html)).

Graph retrieval helps one question type and hurts others. HippoRAG runs personalised PageRank over an LLM-extracted phrase graph. On 2Wiki, where the bridging entity is missing from the question, it raised Recall@5 to 89.5 against 68.2 for ColBERTv2 ([HippoRAG](https://arxiv.org/html/2405.14831)). But on Natural Questions, its first version scored **44.4 against 75.4 for a dense retriever** ([HippoRAG 2](https://arxiv.org/html/2502.14802)). HippoRAG 2 fixed this in two ways. It keeps the base retriever's signal inside the PageRank seeds, weighting passage nodes by retriever similarity × 0.05, which was worth 6.1 Recall@5 points in ablation. And it links the query to whole triples rather than single nodes, which was worth 27.5 points. It reached 59.8 average F1 against 57.0 for NV-Embed-v2 and was never worse on any of seven datasets. Every linking step, however, uses embeddings, and no lexical-only variant was tested ([HippoRAG 2](https://arxiv.org/html/2502.14802)).

Independent comparisons point the same way. They find plain RAG matching or beating graph methods on single-hop facts. GraphRAG's global search answered unanswerable queries correctly only 19.27% of the time, against 96.01% for RAG, and the extracted graphs held only about 65.8% of answer entities ([RAG vs GraphRAG](https://arxiv.org/html/2502.11371)). Global search also spends about 331k prompt tokens per query ([GraphRAG-Bench](https://arxiv.org/html/2506.05690)). Reproductions of LightRAG disagree wildly: 6.6 average F1 in one ([HippoRAG 2](https://arxiv.org/html/2502.14802)) and 58–63 fact-retrieval accuracy in another ([GraphRAG-Bench](https://arxiv.org/html/2506.05690)). Summary nodes do help lexical search. RAPTOR's summary tree lifted BM25 retrieval on NarrativeQA from 23.52 to 27.93 ROUGE, and a tree built from simple recency windows nearly matched one built by clustering (55.8 vs 56.6 on QuALITY) ([RAPTOR](https://arxiv.org/html/2401.18059)). CORTEX's held-out graph result was **+4.6 points on relational questions (not significant) and −6.2 on control questions** ([progress log](../tests/PROGRESS.md)). That is HippoRAG 1's pattern, and HippoRAG 2's fix is the lesson that transfers.

### Index load time, not scoring, decides the 0.5 s budget

Local measurements show where a process-per-query CLI spends its time. They were taken with this Mac's `/usr/bin/python3` 3.9 on synthetic Zipf text of about 80 tokens per chunk ([local benchmark](<../research_notes/Coding agent memory techniques/bench/bench_output_2026-11-04.txt>)):

| Step | 10k chunks | 100k chunks |
|---|---|---|
| Interpreter start | 53–75 ms | 53–75 ms |
| Load a marshalled dict-of-lists index | 0.65 s | 5.8 s |
| Load packed `array` postings | 0.09 s | 0.20 s |
| Score a content-word query (p95) | 0.2 ms | 1.5 ms |
| Score a query with stopword-like terms (p95) | 4 ms | 49 ms |
| FTS5: new process, open, one query (warm page cache) | 85 ms | 95 ms |
| FTS5: query with stopword-like terms (mean) | 26 ms | 392 ms |

Loading the index, not scoring it, decides whether the 0.5 s budget is met. SQLite's FTS5, bundled with this Python, needs no load step. But it evaluates `bm25()` for every matching row, so stopwords must be stripped, and it fixes k1 = 1.2 and b = 0.75 ([SQLite FTS5](https://www.sqlite.org/fts5.html)). Personalised PageRank by power iteration took 258–333 ms on 10k-node graphs and 1.18 s at 30k nodes. Forward push at ε = 10⁻⁴ took under 1 ms, because a damping factor of 0.5 halves the mass at every hop. The popular `rank_bm25` package has no inverted index and loops over every document for each query term ([rank_bm25](https://github.com/dorianbrown/rank_bm25/blob/master/rank_bm25.py)). CORTEX's search takes about 0.45 s on the 720-log stress corpus ([handoff](../tests/HANDOFF.md)), so the lever is its cache format, not its scoring.

For CORTEX this points to one lexical engine over several document types: passages carrying record keys, records, commit messages and summaries. It would use BM25F-style field weights, remove stopwords and split identifiers in snake, camel and kebab case. Per-posting weights would be stored as packed arrays, with a small delta segment rebuilt on each write; FTS5 is the alternative if its fixed parameters hold up on the dev set. Claude passes two to four phrasings in one call. The script fuses them with RRF and reserves one or two slots for hits that only a graph or a summary found. The prototype's PageRank over subjects and passages already has HippoRAG 2's shape. The evidence says to seed passage nodes from normalised BM25 scores at a small weight, solve by forward push, keep the graph as a re-ranker, and judge it only on fresh relational questions.

## The only coding-memory A/B, +7 points, came from verified code citations

Every coding product now separates two layers: human-owned, version-controlled instruction files, loaded always or by path glob, and an agent-written recall layer. The recall layer is being demoted. Forum threads report that Cursor removed Memories in its 2.1 line; in one thread, staff explained the removal of Custom Modes but gave no reason for Memories ([Cursor forum](https://forum.cursor.com/t/custom-modes-and-memories-gone-in-2-1/143744)). Devin's Knowledge is "deprecated and will be removed" in favour of Skills ([Devin docs](https://docs.devin.ai/product-guides/knowledge)). Windsurf tells users to put anything Cascade must reuse reliably in a Rule or AGENTS.md "rather than relying on auto-generated Memories" ([Windsurf docs](https://docs.windsurf.com/es/windsurf/cascade/memories.md)). OpenAI ships Codex Memories off by default, advising users to "treat memories as a helpful recall layer, not as the only source for rules that must always apply" ([Codex docs](https://learn.chatgpt.com/docs/customization/memories?surface=app)). No published effectiveness number turned up for Cursor, Windsurf, Cline's Memory Bank, Codex or Devin memory.

GitHub Copilot Memory is the exception on both counts: it kept its memory layer and published results. Each memory holds a subject, a fact, a reason and citations to code locations such as `src/client/sdk/constants.ts:12`. Before using a memory, the agent checks its citations against the current branch. It stores a corrected version if the code disagrees, and re-stores a validated one to refresh its timestamp. Retrieval was simply the most recent memories for the repository at session start, with search listed as future work. Even so, the A/B tests reported a **PR merge rate of 90% with memory against 83% without**, and 77% against 75% positive feedback on code review, both at p < 0.00001 ([GitHub blog](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/)). Expiry moved from 28 days in the January 2026 preview ([GitHub changelog](https://github.blog/changelog/2026-01-15-agentic-memory-for-github-copilot-is-in-public-preview/)) to a 90-day default that upvotes reset. The docs concede that "Copilot may not catch every outdated fact" ([GitHub docs](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)). The gain came from short, actionable, verifiable facts, not from clever retrieval.

Research on agents that learn from past coding episodes finds small gains from selective memory and losses from unfiltered memory. CTIM-Rover added ExpeL-style cross-task memory to AutoCodeRover and made it worse. On 45 SWE-bench Verified instances it resolved **42% without memory, 40% with it and 31% with memory alone**. Median context grew from 10,027 to 17,807 tokens, because every item was injected up front with no relevance filter ([CTIM-Rover](https://arxiv.org/html/2505.23422v1)). ReasoningBank retrieves a single distilled item per task. It gained 4.6 and 3.4 points on SWE-bench Verified with two Gemini models. Adding failure trajectories helped it, but the same change hurt Agent Workflow Memory on a web task, 44.4 to 42.2 ([ReasoningBank](https://arxiv.org/html/2509.25140v2)). RepoMem's commit-history tools alone lifted file-localisation Acc@5 from 71.6 to 74.3, or 76.5 with file summaries. Repositories with sparse history, however, reportedly fell from 67.4 to 54.3 ([RepoMem](https://arxiv.org/html/2510.01003v2)). Code graphs add similarly little: RepoGraph gained about 2–2.7 points on SWE-bench Lite across four baselines ([RepoGraph](https://arxiv.org/html/2410.14684v2)), and Aider's personalised-PageRank repo map has no published ablation ([Aider](https://aider.chat/2024/05/22/swe-bench-lite.html)). No independent benchmark measures memory across one developer's coding sessions. The closest code-memory benchmark repository publishes no results and ships stub adapters for Mem0 and Zep ([LongMemCode](https://github.com/CataDef/LongMemCode)). That leaves project-specific blind question sets like CORTEX's as the only direct measure.

### Claude Code's own mechanics impose four constraints

Claude Code's documentation fixes four constraints. The first is compaction. Compaction re-injects the project CLAUDE.md, its imports and auto memory from disk, but context that hooks added earlier is "summarized with the rest of the conversation". A SessionStart hook with the `compact` matcher runs again afterwards ([context window docs](https://code.claude.com/docs/en/context-window.md)). The second is transcript retention. Transcripts are plaintext JSONL that include tool outputs and any credentials those outputs printed. A background sweep deletes them after `cleanupPeriodDays`, **30 days by default**, without telling the user ([settings reference](https://code.claude.com/docs/en/settings-reference.md); [.claude directory](https://code.claude.com/docs/en/claude-directory.md)). The third is auto memory. Claude's own auto memory is on by default in local sessions and loads the first 200 lines or 25KB of MEMORY.md into every conversation; when instructions conflict, "Claude may pick one arbitrarily" ([memory docs](https://code.claude.com/docs/en/memory)). The fourth is hook delivery. Hook output reaches Claude as a system reminder capped at 10,000 characters, is discarded if the hook times out, and leaves no visible transcript entry ([hooks reference](https://code.claude.com/docs/en/hooks.md)). The same reference notes three more details: UserPromptSubmit also fires on background-subagent reports and scheduled tasks; `last_assistant_message` is reliable at Stop while the transcript file can lag; and `prompt` and `agent` hook types are synchronous model calls. The no-transcript-entry rule matches CORTEX's finding that injected packs never showed up in stream-json ([progress log](../tests/PROGRESS.md)).

### The capture path is a standing injection channel

An automatic capture path turns a one-time prompt injection into a standing one, and coding agents have already been hit this way. Windsurf's `create_memory` tool ran without approval, letting content from an issue or web page plant persistent instructions ([Embrace The Red](https://embracethered.com/blog/posts/2025/windsurf-spaiware-exploit-persistent-prompt-injection)). Invisible Unicode hid instructions in Cursor and Copilot rules files ([Pillar Security](https://www.pillar.security/blog/new-vulnerability-in-github-copilot-and-cursor-how-hackers-can-weaponize-code-agents)). An npm postinstall payload overwrote MEMORY.md for every Claude Code project, after which Claude recommended committing an API key ([Cisco](https://blogs.cisco.com/ai/identifying-and-remediating-a-persistent-memory-compromise-in-claude-code)). In research settings, MINJA planted records through ordinary queries with **98.2% injection success and 76.8% attack success**, and prompt-level detection caught none of them on two of three agents ([MINJA](https://arxiv.org/html/2503.03704)). AgentPoison exceeded 80% attack success after poisoning less than 0.1% of memory ([AgentPoison](https://arxiv.org/abs/2407.12784)). The defences with published numbers are architectural. Spotlighting, which marks the provenance of every input, cut attack success from over 50% to under 2% ([Spotlighting](https://arxiv.org/abs/2403.14720)). CaMeL, which stops untrusted data from changing control flow, kept 77% task success against 84% undefended ([CaMeL](https://arxiv.org/abs/2503.18813)).

For CORTEX the implications are specific. It should copy the raw text it needs into the project within the 30-day window, redacting secrets and leaving out tool-result bodies, which hold both credentials and untrusted content. Extraction should read only user and assistant text, tag provenance, strip invisible Unicode and reject imperative or command-like statements. The injection block should be presented as delimited evidence that never triggers tools. Critical state should be re-injected from SessionStart `compact`, and the always-loaded overlay kept in files that CLAUDE.md imports. The injection hook should stay silent on subagent reports. Claude's own auto memory should be either disabled or ingested per project, so the two stores never contradict each other. Records that cite code should store `path:line`, the commit and a region hash, and be flagged stale at recall when the hash changes or the symbol disappears. Claude then re-verifies and re-stores them, as Copilot does, and nothing is deleted automatically. Claude Code's own policy of skipping facts that can be derived from the code prevents most staleness in the first place.

## Multi-hop overwrites top out at 28%, so gate and supersede instead of decaying

Knowing what is true after something changed is the weakest ability in every benchmark that tests it. MemoryAgentBench's FactConsolidation task places a contradicting fact after the original. On it, Mem0 averaged 10.0, Zep 5.0, BM25 25.5, long-context GPT-4o 32.5 and GPT-5-mini 53.0, and **no method exceeded 28% on multi-hop consequences**. Even o4-mini fell from 80 to 14 on multi-hop as the context grew from 6K to 32K tokens ([MemoryAgentBench](https://arxiv.org/abs/2507.05257)). HaluMem found most systems missing more than half of the updates, with Mem0 missing 98.51% on long histories. The main cause was that the earlier memory had never been extracted ([HaluMem](https://arxiv.org/html/2511.03506)). Update quality is worth real points: removing reinforcement learning from Memory-R1's update manager dropped its LoCoMo judge score from 62.7 to 52.9 ([Memory-R1](https://arxiv.org/html/2508.19828)). No benchmark tests a system with explicit supersession links, so CORTEX's chains are a reasoned bet without external validation.

The production designs agree on the mechanism, and neither publishes accuracy for it. Mem0 retrieves the ten most similar memories for each new fact and lets one LLM call choose add, update, delete or no-op. Its delete destroys history; its graph variant instead marks conflicting relations invalid ([Mem0](https://arxiv.org/html/2504.19413)). Graphiti, Zep's open-source library, looks for duplicates only among edges between the same two entities, and reuses exact normalised matches without a model call. It invalidates an old edge only when the two facts overlap in time. It compares event dates rather than ingestion order, so facts that arrive out of order still close the right edge ([Graphiti code](https://raw.githubusercontent.com/getzep/graphiti/main/graphiti_core/utils/maintenance/edge_operations.py)). Its judge prompt is a ready-made rule set. A contradiction requires that the facts "cannot both be true", plus explicit evidence that the old fact ended or was replaced. Recency alone never counts as a contradiction. Ownership facts coexist with progress updates. Facts with different numbers or dates are never duplicates ([Graphiti prompt](https://raw.githubusercontent.com/getzep/graphiti/main/graphiti_core/prompts/dedupe_edges.py)). Both designs share a ceiling: a conflict that the candidate search never surfaces is never judged. That makes subject linking the choke point for update recall.

Controlling what enters memory matters far more than forgetting. Across four agents, Xiong and colleagues found that **strict, quality-gated addition beat adding everything by 15.5 to 25.5 points**. Deletion with a strict evaluator moved results between −1.2 and +4.2 points, and periodic time-based deletion lost up to 4.6. With a coarse evaluator, deletion hurt ([Xiong et al.](https://arxiv.org/abs/2505.16067)). Time decay has no supporting ablation. MemoryBank's Ebbinghaus curve is, in its authors' words, "an exploratory and highly simplified memory updating model", and no experiment isolates it ([MemoryBank](https://arxiv.org/abs/2305.10250)). Generative Agents' recency and importance terms were never ablated either ([Generative Agents](https://arxiv.org/html/2304.03442)). In a coding project, a three-month-old architecture decision that was never superseded is still true. Validity, not age, decides what is current.

Offline consolidation has thin evidence for factual recall. Sleep-time compute, from Letta-affiliated authors, cut test-time compute about fivefold at equal accuracy. When related queries shared a context, it cut cost per query 2.5×. Both results come only from stateful maths benchmarks, and the gains tracked how predictable the queries were ([sleep-time compute](https://arxiv.org/abs/2504.13171)). Letta's product splits the work so that the primary agent cannot edit core memory and a background agent rewrites it ([Letta](https://www.letta.com/blog/sleep-time-compute)). That is the split CORTEX's guard already enforces with script-owned files. Generative Agents' reflection was measured on believability (TrueSkill 29.89 with reflection, 26.88 without), and its authors list embellishment among the failure modes ([Generative Agents](https://arxiv.org/html/2304.03442)). Zep reports that incrementally maintained communities drift and need periodic full refreshes ([Zep](https://arxiv.org/html/2501.13956)). Precomputed per-subject pages pay off only when the same subjects come up repeatedly. Consolidated outputs belong in separate records linked to their sources, which an append-only store already guarantees.

Abstention is both under-measured and harmed by extra context. LongMemEval has only 30 abstention questions in 500. Vendor evaluations on LoCoMo drop its adversarial category, which makes up about a quarter of the original questions. Where abstention is measured, more context means less of it. LoCoMo's adversarial F1 fell **from 31.9 to 17.0 as retrieval grew from the top 5 to the top 50 dialog turns** ([LoCoMo](https://arxiv.org/abs/2402.17753)). Adding retrieved context cut Gemini 1.5 Pro's abstention rate from 100% to 18.6%. The same study found two more things. Combining a sufficiency label with the model's own confidence in a small logistic regression raised accuracy on answered questions by 2–10%. Fine-tuning a model to say "I don't know" did not help ([Sufficient Context](https://arxiv.org/abs/2411.06037)).

CORTEX's lifecycle work should therefore go into three measured gates and no clocks. The first is the capture gate, whose precision, measured on labelled turns, is worth more than any pruning rule. The second is the conflict judge. It should use Graphiti's rules, draw candidates from BM25 over statements plus subject linking, and compare `valid_from` rather than `recorded_at`. It should be scored for precision and recall on the synthetic corpus's planted supersessions, with false supersessions counted separately because they silently hide valid memory. The third is the injection hook, which should send nothing, or an explicit "no matching record", when query terms go unmatched, no subject is linked or the top scores are flat. Its thresholds should be fitted on the dev set and checked on fresh questions. Recency or a recall-strength score can break ties among current records on one subject, but it never hides a record.

## Leaderboard margins are mostly artefacts, and 90 questions resolve only 8 points

### Who ran the rival system moved Zep's score by 9 points

The 2025 dispute between Mem0, Zep and Letta shows how little a vendor's LoCoMo ranking means. Zep scored 65.99 when Mem0 ran it and 75.14 when Zep did. Zep blamed misconfigured speaker roles, timestamps and sequential searches ([Zep](https://www.getzep.com/blog/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/)). Across four teams and two backbones, Zep's score ranged from 59.22 to 79.09. MIRIX reported 85.38 for itself, while MemOS's re-run with a different backbone gave 64.33 ([MIRIX](https://arxiv.org/html/2507.07957); [MemOS](https://arxiv.org/html/2507.03724)). An audit, by authors reportedly tied to a competing project, found three problems. 6.4% of LoCoMo's golden answers are wrong, which caps honest scores near 93.6%. An LLM judge accepted **62.81% of deliberately vague wrong answers**. And an EverMemOS claim of 92.32% was reproduced by third parties at 38.38% ([locomo-audit](https://github.com/dial481/locomo-audit)). LongMemEval claims above 90% ride on newer readers, and one vendor concluded that "RAG-like methods have largely solved" the benchmark ([Emergence](https://www.emergence.ai/blog/sota-on-longmemeval-with-rag)).

The pattern extends to architectures. "Memory operating system" designs fall back in other teams' runs; MemoryOS scored 44.80 against 56.80 for plain full text on LongMemEval-S ([LightMem](https://arxiv.org/html/2510.18866)). Fact-and-graph memory products score about half of BM25 on the one independent benchmark that tests both. GraphRAG's and LightRAG's wins are LLM pairwise preferences, which can reverse when the order of presentation changes ([RAG vs GraphRAG](https://arxiv.org/html/2502.11371)). Sleep-time compute is demonstrated only on maths, and decay has never been ablated. What holds up is narrower: Mem0's cost and latency savings, LongMemEval's ablations, MemoryAgentBench's BM25 result, HippoRAG 2's ablations, doc2query--, Copilot's A/B, CTIM-Rover's negative result, Xiong's addition-versus-deletion study and the Sufficient Context abstention findings.

### LLM judges rank systems well and score them badly

LLM judges add their own noise. In "Judging the Judges", the best judges reached chance-corrected agreement (Scott's π) in the high 80s, against 96.2 between humans. Judges with over 90% raw agreement still mis-scored by more than 10 points. When an answer did not meet the criteria, most judges still marked it correct well over half the time, up to 0.99, and some accepted dummy answers like "Yes". Yet even weak judges ranked systems almost perfectly (Spearman ρ 0.98–0.99) ([Thakur et al.](https://arxiv.org/abs/2406.12624)). Identical judge runs disagree with themselves, and forcing temperature 0 lowers agreement with humans ([Rating Roulette](https://arxiv.org/abs/2510.27106)). Decomposed checklists raise both agreement with humans (46.4% to 52.2% in TICK) and consistency between judges ([TICK](https://arxiv.org/abs/2410.03608); [CheckEval](https://arxiv.org/abs/2403.18771)). LongMemEval's judge exceeded 97% agreement with experts but was weakest on abstention ([LongMemEval](https://arxiv.org/html/2410.10813)). CORTEX's judge grades each fact and takes the majority of three Haiku runs, which follows the checklist evidence. But its validation reports raw agreement rather than π: 5 of 40 self-disagreements, and agreement with Sonnet on 33–34 of 40. And the fix that made it more lenient points in exactly the direction the leniency research warns about ([progress log](../tests/PROGRESS.md)).

### Detecting a 5-point gap takes about 250 fresh questions

Miller's error-bar method sets the arithmetic ([Miller](https://arxiv.org/abs/2411.00640)). Comparisons should use paired per-question differences. At 80% power and α = 0.05, the minimum detectable effect is about 2.8 standard errors, and in his worked example detecting a 3-point gap takes about 969 questions. Repeated runs shrink only the within-question share of the variance, by at most two-thirds. Questions that come in groups need clustered standard errors, which ran up to 3.05 times the naive ones. A large IR simulation recommends the paired t-test or a permutation test. It found the bootstrap-shift test biased toward small p-values at small sample sizes ([Urbano et al.](https://arxiv.org/abs/1905.11096)).

Back-calculated from CORTEX's held-out confidence interval for v7 − v5 (−9.4 to +2.2 points), the standard error is about 3.0 points and the **minimum detectable effect about 8.3 points**. Detecting the observed 3.6-point gap would need about 480 questions; a 5-point gap, about 250; a 10-point gap, about 62. The graph's pre-registered bar was at least +10 points with a CI excluding zero, on 60 relational questions. It had roughly even odds of passing even if the true effect were exactly +10, and about one in four at the observed +4.6. So "fails the bar" is the right decision, but it is weak evidence that the graph does nothing. Ten abstention questions carry about ±19 points; getting to ±6 needs about 100.

Fresh questions are the scarcest resource. GSM1k, a newly written mirror of GSM8k, exposed accuracy drops of up to 8%, larger than the gaps CORTEX is trying to resolve ([GSM1k](https://arxiv.org/abs/2405.00332)). The 90-question held-out set has already served one before-and-after decision. Judge-free retrieval metrics avoid judge noise but carry over to accuracy only partly. LongMemEval's +9.4% recall became +5.4% accuracy, and CORTEX's ratio was closer to 0.3. eRAG makes per-document utility labels by feeding each retrieved item to the reader on its own; these tracked end-to-end quality better than relevance labels (Kendall τ up 0.168–0.494) ([eRAG](https://arxiv.org/abs/2404.13781)).

The next evaluation should be designed backwards from the claim it must support. It needs a fresh set: the synthetic corpus, or questions written only from chats after a freeze date. That set should hold about 250 questions for a 5-point claim. Each arm should run three or four times. Results should report a paired t-test beside the bootstrap, with standard errors clustered by source chat. Abstention should be scored on its own set of about 100 questions. The judge needs negative controls in every run: an empty answer, "Yes", a fluent answer about the wrong project, and a plausible answer with one wrong fact. Agreement should be reported as π rather than raw agreement. The judge also needs a one-time calibration against about 150 human-graded answers, the size ARES uses for prediction-powered confidence intervals ([ARES](https://arxiv.org/abs/2311.09476)). Because injection leaves no transcript entry, the hook should log each pack it sends, so retrieval failures can be told apart from reading failures.

### Five questions no study has answered

Five questions remain unmeasured anywhere in this literature, and they bound every recommendation above. First, no study evaluates cross-session memory for a coding assistant on a real developer's project with blind questions. Second, LongMemEval's key-versus-rank merging comparison and its time-aware query expansion exist only for a dense retriever, so their behaviour with BM25 is inferred. Third, no vendor publishes the accuracy of its update decisions, and nobody measures the false-supersession rate that silently hides valid memory. Fourth, LLM-generated document expansion (doc2query with Haiku or GPT as the generator) has no published BM25 result. Fifth, no study measures how precisely code-anchored staleness flags catch outdated memories, or whether they improve answers to history questions rather than to code-change tasks.

## Conclusion

The literature answers the strategic question in CORTEX's handoff. Records-first retrieval, which returns extracted facts as the evidence, is the configuration the controlled studies find lossy. The configuration they support uses records as index keys and as a current-state layer over a raw transcript layer, beneath a curated core that is read whole. That is the handoff's option (a) extended with a transcript layer, not more records-first tuning. It also changes what v7's components are for: the extractor, the supersession chains and the conflict judge keep their value as indexers and keepers of current state, while their output stops competing with the text it was extracted from. The project's own numbers fit the same picture. Curated notes plus grep lead; records-first trails by a margin the harness cannot yet resolve; and better retrieval moved accuracy far less than recall, which points at the reader.

The constraints are less limiting than they look. The techniques with evidence are almost all index-time work or decisions about what the reader sees. The expensive query-time steps (rewriting, reranking, iterating) are things Claude already does inside its own turn at no extra call. The open risk is in evaluation, not architecture. No external benchmark covers this use, so CORTEX's blind question sets are the only direct measurement available. The harness deserves the same investment as the store: enough fresh questions to resolve 5-point effects, calibrated judges, and losses published alongside wins. That investment decides whether any of the ranked techniques can be shown to work here.
